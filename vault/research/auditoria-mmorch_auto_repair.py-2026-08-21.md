Se identificaron 8 hallazgos: 2 bugs de comportamiento, 1 violación estructural del ADR 0001, 2 violaciones de principios, y 3 hallazgos menores. Los más críticos son la releída innecesaria de disco y el path hardcodeado de Windows que rompe portabilidad.

## Findings (sobrevivieron refutacion 8/8 — 1 estructurales, 3 bugs, 2 de principios)

- **Violación del ADR 0001: relee nightly.jsonl del disco cuando el llamador YA tiene el record en memoria** [alta/estructural]: Líneas 63-66: `if rec is None:` lee nightly.jsonl del disco. El docstring (líneas 55-57) dice que nightly.py YA pasa `rec` en memoria. El fallback a disco es código muerto que viola el principio 'estado en memoria, no releer disco'. Si nightly.py cambia y deja de pasar `rec`, este módulo silenciosamente repara lo de ANOCHE en vez de lo de HOY — bug latente por acoplamiento oculto. Debería ser `rec: dict` obligatorio o fallar ruidosamente.
- **Path hardcodeado de Windows en gate_cmd rompe portabilidad** [media/bug]: Línea 91: `--basetemp={Path(repo_dir).drive}/Users/map12/AppData/Local/Temp/claude/pt-repair` usa `.drive` (C:) y un path absoluto de un usuario específico. En Linux/macOS esto produce un path inválido como `/Users/map12/...` (con `.drive` vacío). El gate fallaría con error de pytest, bloqueando TODA reparación. Debería usar `tempfile.mkdtemp()` o `Path(tempfile.gettempdir()) / 'pt-repair'`.
- **Estado de reparación se escribe ANTES del intento de automerge, perdiendo el resultado** [media/bug]: Líneas 99-101: `atomic_write_json(state_path, state)` se ejecuta antes del bloque de automerge (líneas 104-112). Si `try_automerge` falla o mergea, ese resultado NO se persiste en `repair_state.json`. En la próxima corrida, `pick_finding` verá `result: 'built'` y `retry_after` futuro, pero no sabrá si el merge fue exitoso — el estado queda incompleto. El estado debería escribirse DESPUÉS del automerge, incluyendo `out['automerge']`.
- **`wt.close(keep_branch=keep)` puede perder el branch si el build falla pero el estado ya se escribió** [media/bug]: Líneas 118-119: `keep = state.get(sig, {}).get('result') == 'built'` — pero `state[sig]` se escribió en línea 99 con `result: res.get('status', 'fail')`. Si `res['status']` es 'built' pero luego `wt.capture` falla (línea 97), el branch se mantiene pero el commit no se hizo — el branch queda con cambios sin commitear. El `keep` debería basarse en si `wt.capture` tuvo éxito, no solo en el status del build.
- **Violación del principio de inyección: `_default_build` importa `build_project` con acoplamiento oculto a firmas** [media/principio]: Líneas 47-50: `_default_build` hace `from mmorch.project_integrate import build_project` y llama con `max_fix=3, max_gen_calls=40`. Si `build_project` cambia su firma (agrega/quita parámetros), `auto_repair` revienta silenciosamente en runtime. El principio dice 'inyectar deps para que el seam sea donde el self-check sustituye un fake' — pero aquí el default está acoplado a una firma específica sin verificación. Debería haber un self-check que valide la firma o un wrapper que aísle el cambio.
- **El módulo no tiene self-check (`__main__`) — viola el principio de 'todo módulo no-trivial deja un self-check ejecutable'** [media/principio]: El módulo tiene lógica compleja (parsing de records, firma, ventana de reintento, gate) pero NO tiene bloque `if __name__ == '__main__':` con self-check. Los principios dicen explícitamente 'Every non-trivial module leaves a runnable __main__ self-check'. Sin esto, no hay forma de verificar que `findings_from_record`, `_sig` y `pick_finding` funcionan sin correr el nightly completo. Debería haber un self-check que pruebe con records sintéticos.
- **Filtro de artefactos efímeros es frágil: substring match en detail puede filtrar errores legítimos** [baja/otro]: Líneas 38-40: filtra por `'mmorch-wt-' not in f['detail']` — si un error legítimo menciona un worktree (ej: 'el módulo mmorch-wt-utils falla'), se filtra silenciosamente. El comentario dice que es 'medido en los 2 primeros runs vivos', pero el criterio es demasiado amplio. Un error real de un módulo cuyo nombre contenga 'mmorch-wt-' sería ignorado sin registro. Debería filtrar por patrón más específico o al menos loggear qué se filtró.
- **`pick_finding` compara fechas como strings ISO — funciona pero es frágil ante formatos** [baja/otro]: Línea 57: `today <= prev.get('retry_after', '')` — compara strings ISO 8601, que ordenan lexicográficamente correcto SOLO si el formato es consistente (YYYY-MM-DD). Si alguien escribe `retry_after` con timestamp (ej: '2026-08-23T10:00:00'), la comparación sigue funcionando, pero si escribe '23-08-2026' (formato europeo), el orden lexicográfico es incorrecto y la ventana de reintento se rompe. Debería parsear con `date.fromisoformat` explícitamente.
