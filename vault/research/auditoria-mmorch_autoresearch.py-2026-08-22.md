Se encontraron 5 hallazgos reales: 2 bugs de comportamiento, 2 problemas estructurales (lectura redundante de disco y acoplamiento oculto), y 1 violación de principio (inyección incompleta).

## Findings (sobrevivieron refutacion 5/5 — 2 estructurales, 2 bugs, 1 de principios)

- **Violación de ADR-0001: fpath.read_text() se llama 3 veces cuando el contenido ya está en memoria** [alta/estructural]: Línea 83: 'base_content = fpath.read_text()' lee el archivo. Línea 99: 'cur = ctx.best if ctx.best is not None else base_content' — si ctx.best existe, ya tenemos el contenido en memoria pero propose() escribe 'cur' al disco (línea 100) y luego score() lo relee implícitamente vía el scorer. Peor: línea 118 'fpath.write_text(res.best)' escribe el resultado final, pero si el scorer ya modificó el archivo (efecto secundario), el write sobreescribe sin verificar. El contenido del archivo se lee/escribe 4+ veces cuando el llamador ya tiene 'base_content' en memoria. Debería pasarse el contenido como parámetro o cachearse en el closure.
- **Acoplamiento oculto: el scorer puede modificar target_file y run_autoresearch no lo detecta** [alta/estructural]: Línea 118: 'fpath.write_text(res.best)' asume que el archivo no cambió durante la corrida. Pero el scorer_cmd se ejecuta con cwd=cwd y shell=True — si el scorer (o cualquier script que corra) toca target_file, el resultado final sobreescribe silenciosamente esos cambios. Peor: propose() escribe el candidato al archivo (línea 100) ANTES de que score() corra, así que el scorer VE el candidato — pero si el scorer lo modifica, la siguiente ronda de propose() lee 'ctx.best' (en memoria, no del disco) y escribe eso, perdiendo la modificación del scorer. Este es un acoplamiento oculto: run_autoresearch depende de que el scorer NO toque target_file, pero no hay ninguna verificación ni documentación de ese contrato.
- **resume_from_journal lee el archivo DOS veces y calcula 'best' de forma inconsistente** [media/bug]: Líneas 44-55: la función primero itera sobre todas las líneas acumulando 'best' con lógica 'best = bs if best is None else best' (que en realidad NO actualiza best con valores mayores, solo mantiene el primero), y luego relee el archivo completo para tomar el último registro. El primer loop es código muerto que nunca actualiza 'best' correctamente — si el primer registro tiene best_score=0.5 y el segundo 0.9, 'best' queda en 0.5 hasta que el segundo bloque lo sobreescribe con 0.9. El primer loop debería eliminarse o corregirse; actualmente es confuso y sugiere que se intentó hacer un max() pero se implementó mal.
- **El journal se escribe con 'best_score' pero resume_from_journal no valida consistencia con rounds** [media/bug]: Línea 52: 'rounds' cuenta TODOS los registros del journal, pero 'best' se toma del último registro. Si el journal se cortó a mitad de una ronda (crash entre propose y score), el último registro puede no tener 'best_score' (None), y entonces 'best' queda con el valor del loop anterior — pero 'rounds' ya contó esa ronda incompleta. Al resumir, se restan rounds_done de max_rounds pero el best puede ser de una ronda anterior, creando una discrepancia silenciosa entre cuántas rondas se reportan hechas y cuál es el mejor score real.
- **run_fn inyectable no recibe el contenido candidato — el seam de testeo es incompleto** [baja/principio]: Línea 76: 'run = run_fn or _default_run' — el inyectable recibe solo 'cmd' (string). Pero el principio de inyección (seam + injection = testability) dice que el seam debe permitir sustituir el comportamiento real. Con la firma actual, un test que quiera simular el scorer necesita: (1) crear un archivo temporal con el contenido candidato, (2) hacer que run_fn lea ese archivo. Pero el contenido candidato ya está en memoria (ctx.best) — el test no puede accederlo sin releer del disco. La firma debería ser run_fn(cmd, content) o run_fn(cmd, candidate_path) para que el test pueda verificar que el scorer recibe exactamente el contenido propuesto, sin depender del filesystem.
