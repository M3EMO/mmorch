El módulo auto_apply.py implementa la política de promoción autónoma con un enfoque fail-closed. Se identificaron problemas estructurales significativos: duplicación de lógica de clasificación entre preflight y reconcile, re-evaluación de estado que ya existe en memoria, y acoplamiento oculto con el estado del runtime. También hay un bug potencial en la verificación de diff_unchanged que podría permitir promociones con diffs no autorizados.

## Findings (sobrevivieron refutacion 10/10 — 5 estructurales, 3 bugs, 1 de principios)

- **Duplicación de lógica de clasificación entre preflight y reconcile** [alta/estructural]: La lógica de clasificación (classify_branch + verificación de diff_hash + preflight_checks) está duplicada en preflight() (líneas ~150-160) y reconcile() (líneas ~330-340). Si la lógica de clasificación cambia (ej: nuevos campos en el dict de clasificación), ambos lugares deben actualizarse. Esto viola el principio de 'Locality: keep what changes together in ONE place'. La clasificación debería ser una función única que ambos llamen.
- **Re-evaluación de estado que ya existe en memoria en reconcile()** [alta/estructural]: En reconcile(), cuando state['status'] == 'candidate', se vuelve a llamar a classify_branch() (línea ~330) para verificar la identidad del candidato. Sin embargo, el estado ya contiene preflight_checks y baseline que fueron validados en preflight(). Re-ejecutar la clasificación es redundante y viola el ADR 0001 (estado en memoria, no releer disco). El estado candidate ya tiene toda la evidencia necesaria; solo debería verificarse que el runtime no haya cambiado.
- **Acoplamiento oculto: reconcile() depende de la estructura interna de preflight_checks** [media/estructural]: En reconcile() línea ~335, se usa `all(state.get('preflight_checks', {}).values())` para verificar que el candidato sigue siendo válido. Esto asume que preflight_checks es un dict de booleanos donde todos deben ser True. Si preflight() cambia la estructura (ej: agrega un campo 'warnings' que no es booleano), reconcile() podría fallar silenciosamente o comportarse incorrectamente. No hay un contrato explícito sobre la forma de preflight_checks.
- **Lógica de rollback duplicada entre rollback() y reconcile()** [media/estructural]: La lógica de revertir un merge (git revert + verificación) está duplicada en rollback() (líneas ~280-300) y reconcile() (líneas ~360-380). Si la lógica de revert cambia (ej: flags de git revert), ambos lugares deben actualizarse. Esto debería extraerse a una función única _perform_revert() que ambos llamen.
- **checked_budget() asume estructura específica del dict de budget** [media/estructural]: checked_budget() (líneas ~125-130) asume que budget_fn() devuelve un dict con claves 'enforced' y 'remaining'. Si budget_status() cambia la estructura (ej: renombra 'remaining' a 'remaining_budget'), checked_budget() fallaría silenciosamente (value.get('remaining') devolvería None, y (None or 0) > 0 sería False). No hay un contrato explícito sobre la forma del dict de budget.
- **Bug: diff_unchanged se marca como True incluso si classification falla** [alta/bug]: En preflight() líneas ~160-163: `checks['diff_unchanged'] = bool(isinstance(classification, dict) and classification.get('diff_hash') == expected_diff_hash)`. Si classification es None (porque capture() falló), diff_unchanged se marca como False correctamente. PERO si classification es un dict sin la clave 'diff_hash' (ej: classify_branch devuelve un dict sin esa clave), diff_unchanged se marca como False. Sin embargo, si classification es un dict con diff_hash=None y expected_diff_hash=None, la comparación `None == None` es True, marcando diff_unchanged como True aunque no haya diff real. Esto podría permitir una promoción sin verificación real del diff.
- **Zona 'yellow' con rollout 'non_red' no verifica límites de archivos** [media/bug]: En preflight() líneas ~170-175: cuando zone == 'yellow' y rollout == 'non_red', se marca yellow_bounded como True sin llamar a bounded_fn. Esto significa que un cambio yellow con 100 archivos modificados y 10000 líneas cambiadas pasaría el preflight si rollout es 'non_red'. El nombre 'non_red' sugiere que solo excluye rojo, pero yellow sin límites podría ser igual de peligroso. Esto contradice el espíritu de 'bounded rollout'.
- **Reconcile() no verifica que el runtime esté en el estado esperado antes de avanzar** [media/bug]: En reconcile(), para state['status'] == 'merged' (línea ~350), solo verifica que head == merge_sha. Pero no verifica que el runtime esté limpio (runtime.clean()) antes de avanzar a 'observing'. Si hay cambios no commiteados en el runtime después del merge, se avanzaría a observing con un runtime sucio, lo que podría causar observaciones inválidas.
- **Violación del principio de inyección de dependencias en checked_goal()** [media/principio]: checked_goal() (línea ~135) llama directamente a goal_guard(allow_init=False) importado de .goal. Esto crea un acoplamiento directo con el módulo goal. Si goal_guard cambia su firma o comportamiento, preflight() se rompe sin que el llamador pueda inyectar un mock. El patrón correcto sería que goal_fn sea siempre inyectado, y checked_goal() solo sea un fallback que use goal_guard importado localmente.
- **Falta de verificación de que el runtime esté en el branch correcto** [baja/otro]: En merge_candidate(), se verifica que runtime.head() == expected_base_sha y runtime.clean(), pero no se verifica que el runtime esté en el branch esperado. Si el runtime está en un branch diferente pero con el mismo head SHA (posible con SHAs colisionantes o si el branch fue movido), la verificación pasaría incorrectamente. Debería verificarse también el branch actual del runtime.
