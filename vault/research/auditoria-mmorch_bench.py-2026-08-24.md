El módulo bench.py es sólido en su diseño general: tasks congeladas como data pura, anti-contaminación con held_out, y materialize que arma repos git reales. Se encontraron 4 hallazgos reales: un bug en la lógica de dedup del test de acceptance (inconsistente con la spec), una violación estructural del principio de estado-en-memoria (releer TASKS del disco en get_task), una violación de principio por acoplamiento oculto con el intérprete de Python, y un hallazgo 'otro' sobre la fragilidad del reemplazo de 'python ' en accept_cmd.

## Findings (sobrevivieron refutacion 4/4 — 1 estructurales, 1 bugs, 1 de principios)

- **get_task relee TASKS del disco cuando el llamador ya tiene la lista en memoria** [media/estructural]: get_task(name) hace una búsqueda lineal sobre TASKS cada vez que se llama. Si un llamador ya tiene la lista de tasks (p.ej. de selection_tasks() o de una iteración), get_task vuelve a recorrer la lista global. Esto viola el principio de 'estado en memoria — no releer disco' (docs/adr/0001): TASKS es una constante global en memoria, pero get_task la trata como si fuera una fuente externa. Peor: si otro módulo mutara TASKS (p.ej. agregando tasks dinámicamente), get_task devolvería resultados inconsistentes con lo que el llamador ya tiene. La solución sería que get_task acepte la lista como parámetro opcional, o que los llamadores usen un dict indexado por nombre construido una sola vez.
- **Bug en test de acceptance: dedup por id no coincide con la spec del task** [media/bug]: En test_normalize_titlecase_dedup_negativos, la spec dice 'dedup por id (queda el primero)' pero el test usa dos filas con id='1' y montos 10.005 y 5.0, esperando len(rows)==1. Sin embargo, la primera fila tiene monto 10.005 que al redondear a 2 decimales da 10.0 o 10.01 (el test acepta ambos), pero la segunda fila con id='1' y monto 5.0 debería ser descartada por dedup. El problema: si el workflow implementa dedup ANTES de redondear, la primera fila (10.005) se queda y la segunda (5.0) se descarta — correcto. Pero si redondea primero, 10.005 → 10.0 y 5.0 → 5.0, y el dedup por id='1' descarta la segunda — también correcto. El bug real: el test no verifica que 'queda el primero' — solo verifica que queda UNO. Un workflow que dedupe quedándose con el ÚLTIMO (no el primero) pasaría este test, violando la spec. El test debería verificar que rows[0]['monto'] == 10.0 o 10.01 (el primero), no solo len(rows)==1.
- **Acoplamiento oculto: materialize depende del intérprete de Python del proceso mmorch** [alta/principio]: En materialize, el comentario dice 'El cmd corre con EL intérprete de mmorch' y usa sys.executable. Esto crea un acoplamiento oculto: si el workflow que consume este accept_cmd se ejecuta en un entorno donde sys.executable no está disponible (p.ej. un contenedor sin el mismo Python, o un worker remoto), el comando fallará silenciosamente. El principio de inyección de dependencias (seam + injection) dice que las dependencias deben inyectarse, no capturarse del entorno. La solución sería que materialize acepte un parámetro python_path opcional, o que el llamador pase el intérprete explícitamente. Además, el reemplazo 'python ' → f'"{sys.executable}" ' es frágil: si accept_cmd no empieza con 'python ' (p.ej. 'python3 -m pytest'), el replace no hace nada y el comando usa el python del sistema.
- **Fragilidad en el reemplazo de 'python ' por sys.executable en accept_cmd** [baja/otro]: materialize hace task.accept_cmd.replace("python ", f'"{sys.executable}" ', 1). Esto solo reemplaza la PRIMERA ocurrencia de 'python ' y solo si aparece exactamente como 'python ' (con espacio). Si un task futuro tuviera accept_cmd = "python3 -m pytest" o "python -m pytest --strict", el replace fallaría silenciosamente (en el primer caso no reemplaza nada; en el segundo reemplaza pero deja '--strict' fuera del quote). Además, si accept_cmd contiene 'python ' en otra posición (p.ej. un path), el replace lo rompería. Más robusto sería parsear el comando con shlex.split y reemplazar el primer token si es 'python'.
