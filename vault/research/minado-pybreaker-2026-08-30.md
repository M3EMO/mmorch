PyBreaker es una implementación madura y bien probada del patrón Circuit Breaker, con soporte para almacenamiento en memoria y Redis, y adaptadores para código síncrono y asíncrono (Tornado). Su valor principal no está en la novedad del patrón, sino en la calidad de su implementación: separación limpia de responsabilidades (estado, almacenamiento, listener), API pequeña y profunda, y un sistema de pruebas exhaustivo que cubre todos los estados y transiciones. Para mmorch, los grafts más valiosos son el patrón de almacenamiento pluggable (que permite inyectar diferentes backends sin cambiar la lógica del breaker) y el diseño de listeners desacoplados (que permite observar y reaccionar a eventos sin acoplar el core). La licencia BSD-3 es permisiva, permitiendo tomar código literal con atribución.

## Grafts (sobrevivieron refutacion 4/4)

- **Patrón de almacenamiento pluggable con estado inyectable** (Medio (2-3 horas): definir la interfaz, refactorizar el orquestador para recibir el storage por inyección, implementar al menos un backend alternativo, escribir self-check con fake.): Extraer el concepto de 'state_storage' como una interfaz separada (CircuitMemoryStorage, CircuitRedisStorage) que el CircuitBreaker recibe por inyección. El breaker no sabe ni le importa dónde se guarda el estado; solo usa la interfaz. Esto permite: (1) testear el breaker con un storage fake sin Redis, (2) cambiar de backend sin tocar la lógica del breaker, (3) compartir estado entre procesos si se usa Redis. El constructor acepta el storage como parámetro con un default sensato (memoria), manteniendo la API pequeña. — aplica a Mmorch: el orquestador multi-modelo necesita un 'state_storage' para el estado de los bandits y el loop de ideas. Actualmente el estado probablemente vive en memoria o en un archivo hardcodeado. Aplicar este patrón: definir una interfaz 'BanditStateStorage' con métodos get/set/update, implementar 'MemoryStorage' y 'RedisStorage' (o 'FileStorage'), e inyectar el storage en el orquestador. Esto permite testear con fakes, escalar a multi-proceso, y cambiar de backend sin tocar la lógica de decisión.. - **Sistema de listeners desacoplados para eventos del ciclo de vida** (Bajo (1-2 horas): definir la interfaz de listener, agregar notificaciones en los puntos clave del orquestador, implementar un listener de logging como ejemplo.): El CircuitBreaker acepta una lista de 'listeners' que implementan una interfaz con callbacks (state_change, failure, success, etc.). El breaker solo notifica; no sabe quién escucha ni qué hace con el evento. Esto permite: (1) logging sin acoplar el core, (2) métricas sin tocar la lógica, (3) alertas en producción. La interfaz es pequeña (4-5 métodos) y los listeners son opcionales (default vacío). — aplica a Mmorch: el flywheel de entrenamiento y el loop de ideas necesitan observar eventos (cuándo un modelo falla, cuándo un bandit cambia de brazo, cuándo se completa una verificación cross-family). Aplicar este patrón: definir 'IdeaLoopListener' con callbacks (on_idea_generated, on_verification_failed, on_bandit_switch), permitir inyectar listeners en el orquestador. Esto separa la lógica de decisión de la telemetría y el logging.. - **Máquina de estados explícita con transiciones validadas** (Alto (4-6 horas): refactorizar el orquestador para usar la máquina de estados, definir las transiciones válidas, escribir tests para cada transición.): PyBreaker modela los estados (closed, open, half-open) como clases separadas (CircuitClosedState, CircuitOpenState, CircuitHalfOpenState) que implementan una interfaz común. Cada estado sabe cómo manejar una llamada (éxito/fallo) y cómo transicionar. El breaker delega en el estado actual; no tiene if/elif para decidir qué hacer. Esto hace que las transiciones sean explícitas, testeables y difíciles de romper. — aplica a Mmorch: el orquestador tiene estados implícitos (entrenando, verificando, explorando, explotando) que probablemente se manejan con flags o if/elif. Aplicar este patrón: modelar el ciclo de vida del orquestador como una máquina de estados explícita (IdleState, TrainingState, VerifyingState, ExploringState), donde cada estado sabe cómo manejar eventos (nuevo dato, fallo de verificación, timeout) y cómo transicionar. Esto reduce bugs de estados inconsistentes y hace el flujo más legible.. - **Decorador con overloads tipados para API dual (sync/async)** (Medio (2-3 horas): definir los overloads, implementar la detección sync/async, escribir typechecks con mypy.): PyBreaker expone el mismo CircuitBreaker tanto para funciones síncronas (call) como asíncronas (call_async), usando overloads de typing para que el type checker sepa cuál es cuál. El usuario no necesita saber si la función es sync o async; el breaker lo maneja. Esto da una API uniforme con seguridad de tipos. — aplica a Mmorch: el orquestador mezcla código síncrono (lectura de archivos, config) y asíncrono (llamadas a APIs de modelos, verificación cross-family). Aplicar este patrón: definir una función 'execute' con overloads que acepte tanto callables sync como async, y que internamente detecte y maneje ambos casos. Esto unifica la interfaz y evita que el usuario tenga que saber si la operación es async..
